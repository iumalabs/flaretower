# Quickstart: Workers & Access Exposure

**Feature**: [spec.md](./spec.md) | **Date**: 2026-08-07

Validation guide for proving this module works end-to-end once implemented.
Not implementation code — see `tasks.md` (generated by `/speckit-tasks`) for
that.

## Prerequisites

- A Cloudflare account with:
  - At least 2-3 test Workers in varying exposure states (one with a
    custom domain behind Access, one with `workers.dev` enabled and
    unprotected, one fully private) — set up manually in a scratch/test
    account, not production.
  - A Zero Trust / Access setup with at least one application using a
    meaningfully-restrictive policy and one using an "Allow — Everyone"
    policy, for User Story 3.
- A Cloudflare API token scoped exactly per `research.md` §3's table
  (`Workers Scripts Read`, `Workers Routes Read`,
  `Access: Apps and Policies Read`) — read-only, per constitution
  Principle VIII.
- `wrangler secret put CF_API_TOKEN` (or equivalent name chosen during
  implementation) — never as a `vars` entry (constitution Principle VIII).
- FlareTower itself deployed and reachable only through its own Access
  application (constitution §6/§7) — this module's endpoints are validated
  *through* that gate, not by bypassing it.

## Scenario 1 — full inventory (User Story 1)

1. Deploy FlareTower against the test account above.
2. As an Access-authenticated operator, call
   `GET /api/exposure/inventory` (or open the equivalent UI screen once
   built).
3. **Expect**: every test Worker appears exactly once; each hostname it has
   (custom domain / `workers.dev` / Preview URL) is listed with its own
   independent status — not merged into a single per-Worker verdict.

## Scenario 2 — critical flag on unprotected exposure (User Story 2)

1. Using the test Worker with `workers.dev` enabled and no Access
   application covering it.
2. Call `GET /api/exposure/inventory`.
3. **Expect**: that hostname's `status` is `"critical"`, with a `reason`
   naming the absence of Access coverage. Its custom domain (if separately
   Access-protected) shows a different, non-critical status in the same
   response.

## Scenario 3 — effectively-open Access policy (User Story 3)

1. Using the test Access application whose only policy is "Allow —
   Everyone".
2. Call `GET /api/exposure/inventory`.
3. **Expect**: the hostname it covers shows `status: "warning"`, not
   `"safe"` — distinguishable from both the critical (no Access at all) and
   safe (meaningfully restricted) cases.

## Scenario 4 — scheduled drift detection, new-vs-repeat (User Story 4)

1. Trigger the `scheduled` handler locally: `wrangler dev --test-scheduled`,
   then `curl "http://localhost:8787/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"`
   (per the platform's documented local Cron Trigger testing flow).
2. **Expect**: a run completes, and any hostname in `critical`/`warning`
   state produces a row in `GET /api/exposure/alerts` if it wasn't already
   alerted (fresh test account run — this covers the "no grace period on
   first run" edge case too).
3. Trigger the scheduled handler a second time with no underlying change to
   the test account.
4. **Expect**: no new alert rows are created for the still-critical/warning
   hostnames (FR-009, SC-005) — `GET /api/exposure/alerts` returns the same
   set as after step 2, not a duplicate.
5. Change one previously-safe test hostname to unprotected (e.g. attach a
   new `workers.dev`-enabled Worker with no Access app), trigger the
   scheduled handler again.
6. **Expect**: exactly one new alert row appears for that hostname
   (FR-008).

## Scenario 5 — partial-evaluation transparency (Edge Cases / FR-011)

1. Temporarily scope the test API token down further (remove
   `Access: Apps and Policies Read`) or point it at an account/zone it
   can't fully see.
2. Call `GET /api/exposure/inventory`.
3. **Expect**: affected hostnames show `status: "not_evaluated"` with a
   `reason` naming the scope/permission gap — never silently reported as
   `"safe"`.

## Scenario 6 — no unauthenticated access (cross-cutting, Principle II)

1. Call any `/api/exposure/*` endpoint with no `Cf-Access-Jwt-Assertion`
   header, and again with a tampered/expired one.
2. **Expect**: `403` in both cases, with no exposure data in the response
   body.
